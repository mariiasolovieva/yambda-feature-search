# Feature engineering для рекомендательных систем

## Постановка задачи

Задача классификации: предсказать, заинтересованность пользователя по проценту прослушивания трека -- понравился (1) или не понравился (0).

Конкретный исследовательский вопрос, поставленный в тестовом задании: можно ли автоматизировать построение признаков для рекомендательных систем и сохранить качество модели по сравнению с ручным feature engineering.

В качестве baseline используется CatBoost, а затем сравнение с подходами к автоматической генерации и отбору признаков.

## Данные

Используется датасет [Yambda от Яндекса](https://huggingface.co/datasets/yandex/yambda).

Основные поля:
- `uid` — пользователь;
- `item_id` — музыкальный трек;
- `timestamp` — время события;
- `event_type` — тип события (`listen`, `like`, `unlike`, `dislike`, `undislike`);
- `is_organic` — признак органического взаимодействия (пользователь сам выбрал и включил трек, без рекомендаций);
- `played_ratio_pct` — доля прослушанного трека;
- `track_length_seconds` — длительность трека.

Для экспериментов выбрана случайная выборка из 100 пользователей с сохранением полной истории их событий (сокращение выборки для реализации кода на личных ресурсах). Используется фиксированный seed `42`.

Файл данных: `data/events_sample.parquet`.

## Технические этапы работы

1. Подготовлена случайная выборка пользователей и их событий (`src/download_data.py`).
2. Изучены типы взаимодействий и логика лайков.
3. Создан `src/analyze_played_ratio.py` — общий анализ датасета и определение порога заинтересованности по проценту прослушанного трека.
4. Создан `src/build_features.py` — построение ручных признаков (43 признака в четырёх группах).
5. Создан `src/split_data.py` — временной split train / val / test (70 / 15 / 15) с sanity-проверками.
6. Создан `src/train_baseline_dummy.py` — naive baseline (DummyClassifier) и oracle как нижняя и верхняя границы качества.
7. Создан `src/train_baseline.py` — CatBoost на ручных признаках.
8. Создан `src/train_baseline_ablation.py` — ablation по группам признаков.
9. Создан `src/auto_features.py` — автоматическая генерация и отбор признаков через DSL и grid search, включая автоматический подбор временного окна.
10. Создан `run_exp.py` — end-to-end пайплайн для воспроизведения всех результатов одной командой.

## Как воспроизвести

1. Установить зависимости: `pip install -r requirements.txt`
2. Запустить пайплайн: `python run_exp.py`
3. Все артефакты появятся в `results/`

Органические прослушивания заметно короче — пользователь, самостоятельно включивший трек, чаще «проверяет» его и переключает, если не зашло. Рекомендательные прослушивания чаще доходят до конца — возможно за счет фонового воспроизведения, либо рекомендации позволяют найти абсолютно новую музыку, которую пользователь еще не слышал, поэтому требуется больше времени на оценку. Таким образом, `is_organic` — обязательный признак в модели. Без него модель смешивает два принципиально разных режима потребления контента.

### Связь `played_ratio_pct` с лайками

Высокий `played_ratio_pct` не является дескриптором явного интереса (лайка). Медианный лайк ставится после прослушивания ~19% трека, а не после полного. Пользователь часто распознаёт трек за 10–20 секунд и лайкает, не дослушивая.

## Методология на основе анализа датасета

На основании анализа зафиксированы следующие решения для baseline и последующих экспериментов.

**1. Целевая переменная.** В качестве основного target выбирается бинаризация `played_ratio_pct` с порогом 50%:

- `label = 1`, если `played_ratio_pct >= 50`;
- `label = 0` — иначе.

Обоснование:

- порог 50% совпадает с официальным определением «прослушано» в датасете Yambda и отражает принцип «отклик на показ»;
- баланс классов (~66/34) не требует агрессивного ресемплинга;
- **предсказываем, прослушает ли пользователь трек хотя бы наполовину**.

**2. Исключение нулевых прослушиваний.** События с `played_ratio_pct == 0` (8.22%) исключаются из обучающих данных: это мгновенные старты без реального прослушивания. После фильтрации positive rate при пороге 50% составляет ~72%.

**3. Роль лайков.** Лайки не используются как target, но сохраняются как признаки и как явный сигнал релевантности.

**4. `is_organic` как обязательный признак.** Разрыв в распределении `played_ratio_pct` между органическими и рекомендательными прослушиваниями слишком велик, чтобы его игнорировать.

**5. Метрики оценки.** Для baseline зафиксированы:

- `LogLoss` и `ROC-AUC` — контроль калибровки и общего качества классификации;
- `NDCG@10` и `Recall@10` — оценка качества ранжирования.

Подбор гиперпараметров модели проводится на validation, финальная оценка — на отложенном test.

**6. Схема валидации.** Разбиение на train / validation / test — по времени (без перемешивания), с сохранением полной истории каждого пользователя. Все признаки для пары `(user, item, t)` рассчитываются только по событиям с `timestamp < t`.

## build_features

Скрипт `src/build_features.py` превращает события в таблицу признаков, из которой затем строится baseline.

### Вход и выход

Выбор и загрузка данных случайных 100 пользователей производится через `src/download_data.py` и проверка через `src/check_data.py`.

- **Вход:** `data/events_sample.parquet` (события Yambda).
- **Выход:** `results/features.parquet` — одна строка = одно `listen`-событие (пара `user–item` в момент `t`), колонки = признаки.
- **Размер:** 514 016 строк × 48 колонок на текущей выборке 100 пользователей.

### Предобработка

- Берутся только события `listen`, `like`, `unlike`, `dislike`, `undislike`.
- Исключаются `listen`-события с `played_ratio_pct == 0` (8.22% от всех прослушиваний) — это «старт и мгновенный уход», не прослушивание.
- Целевая переменная: `label = 1`, если `played_ratio_pct >= 50`, иначе `0`. Positive rate после фильтрации нулей — 71.79%.

### Группы признаков

Всего 43 признака в четырёх группах. Для каждой пары `(user, item, t)` признаки строятся строго по событиям с `timestamp < t` — "утечки будущего" нет.

**1. Признаки пользователя (`u_*`, 16 шт.).** По всей истории пользователя до `t`:
- All-time: `u_n_events`, `u_n_listens`, `u_n_likes`, `u_n_dislikes`, `u_like_rate`, `u_mean_played_ratio`.
- "Оконные" (`7d`, `30d`): `u_n_listens_{W}d`, `u_n_likes_{W}d`, `u_mean_played_ratio_{W}d`, `u_like_rate_{W}d`.
- Recency / tenure: `u_days_since_last_event`, `u_days_since_first_event`.

**2. Признаки трека (`i_*`, 14 шт.).** По всей истории трека до `t` — аналогичный набор: счётчики событий, `i_like_rate`, `i_mean_played_ratio`, оконные версии за 7 и 30 дней, `i_days_since_last_listen`, `i_days_since_first_listen`.

**3. Признаки пары `user–item` (`p_*`, 10 шт.).** По совместной истории пользователя и трека до `t`:
- All-time: `p_n_events`, `p_n_listens`, `p_n_likes`, `p_n_unlikes`, `p_n_dislikes`, `p_mean_played_ratio`.
- `p_user_has_liked_item` — лайкал ли пользователь этот трек и не снял лайк.
- Оконные: `p_n_listens_{W}d` (только число прослушиваний — пары слишком разрежены для более сложных агрегатов).
- Recency: `p_days_since_last_listen`.

**4. Контекстные признаки (`ctx_*`, 3 шт.).** Известны в момент старта прослушивания, без истории: `ctx_track_length_sec`, `ctx_log_track_length`, `ctx_is_organic`.

### Окна времени

Используются три режима: **all-time** (вся история до `t`), **7 дней**, **30 дней**. Логика «окно N» реализована как параметр: для каждого базового агрегата создаётся отдельная колонка на каждое значение `W` из `WINDOWS_DAYS = (7, 30)`. Для автоподбора далее используются окна (1, 3, 7, 14, 30).

### Защита от утечек

Все агрегаты считаются через `pd.merge_asof` с запросом на момент `t - 1`, то есть строго до текущего `listen`-события. Это касается и оконных признаков, и recency, и tenure: событие, для которого предсказывается `label`, никогда не попадает в собственные признаки. Сплит train/val/test тоже будет по времени (см. раздел `split_data`), поэтому временна́я структура сохраняется на всех этапах.

## split_data

Скрипт `src/split_data.py` делит таблицу признаков на train / val / test. Ключевая идея — делим выборки строго по времени, без перемешивания: все события train раньше всех событий val, все события val раньше всех событий test.

### Почему не `train_test_split`

Задача устроена так, что признаки для пары `(user, item, t)` считаются по событиям с `timestamp < t`. При случайном разбиении соседние по времени события попадут в разные сплиты, и признаки test-строк окажутся построены из событий train — это утечка будущего. Временной сплит её исключает по построению и имитирует реальную эксплуатацию: учимся на всём, что было до даты T, проверяем на том, что случилось после неё.

### Вход и выход

- **Вход:** `results/features.parquet`.
- **Выход:** `results/train.parquet`, `results/val.parquet`, `results/test.parquet`.
- **Пропорции:** 70% / 15% / 15% по квантилям `timestamp` (параметры `TRAIN_FRAC`, `VAL_FRAC`).

### Результат на текущей выборке

| Сплит | Строк | Positive rate | Пользователей | Треков | Диапазон timestamp |
|---|---:|---:|---:|---:|---|
| train | 359 811 (70.0%) | 72.37% | 84 | 56 002 | 3 280 … 20 353 890 |
| val | 77 102 (15.0%) | 69.24% | 91 | 26 256 | 20 354 000 … 23 360 300 |
| test | 77 103 (15.0%) | 71.62% | 98 | 28 411 | 23 360 315 … 25 999 815 |

Дрейф `pos_rate` между train и test — 0.75 п.п. (ниже порога 5%), между train и val — 3.13 п.п. Это означает, что распределение целевой переменной стабильно и модель можно оценивать на отложенных данных без поправок.

### Sanity-проверки

Скрипт выполняет четыре проверки и печатает предупреждения, если что-то не так:

1. **Temporal order.** `train.max(timestamp) < val.min(timestamp) < test.min(timestamp)` — утечки будущего по построению нет.
2. **User overlap.** Считается пересечение пользователей train и test. На текущей выборке: 84 из 98 test-пользователей есть в train, 14 cold-start пользователей.
3. **Cold-start share.** Доля test-строк, приходящихся на cold-start пользователей — 16.33% (12 590 строк). Для этих строк признаки `u_*` и `p_*` нулевые, модель опирается только на `i_*` и `ctx_*`. Это реалистичный сценарий (новые пользователи), но при интерпретации метрик test важно помнить, что они смешивают «тёплых» и cold-start пользователей.
4. **Pos-rate drift.** Предупреждение, если `pos_rate` в val или test отклоняется от train больше, чем на 5 п.п.

## Baseline (1): CatBoost на ручных признаках

Первый baseline обучен на всех 43 ручных признаках из `results/features.parquet`. Модель — `CatBoostClassifier` с `Logloss`, `early_stopping_rounds=100` по валидации. Скрипт: `src/train_baseline.py`. Артефакты: `results/catboost_baseline.cbm`, `results/baseline_metrics.json`, `results/baseline_test_preds.parquet`, `results/baseline_feature_importance.csv`.

### Параметры обучения

- 470 итераций до early stopping (из 2000 возможных), обучение ~7 секунд.
- Best iteration: 470. Best val Logloss: 0.2122.
- `scale_pos_weight` не используется: положительный класс 72%, дисбаланс в обратную сторону.

На обучении это работает как сильный сигнал (в сессии `played_ratio` выше), но подавляет важные признаки.

## Naive baselines (2): нижняя и верхняя граница качества

Чтобы понять, насколько хорош CatBoost, нужны две точки отсчёта: «глупая» модель без обучения и «идеальная» модель. Скрипт `src/train_baseline_dummy.py` считает обе.

`DummyClassifier(strategy="prior")` всегда предсказывает тренировочное распределение классов (neg=0.276, pos=0.724) и не учится. Это «нулевая» модель.

| Сплит | LogLoss | ROC-AUC | NDCG@10 | Recall@10 |
|---|---:|---:|---:|---:|
| val | 0.6196 | 0.5000 | 0.6528 | 0.0549 |
| test | 0.5966 | 0.5000 | 0.6811 | 0.0780 |

ROC-AUC = 0.5 — все прогнозы одинаковы, ранжирование невозможно. LogLoss разный на val и test, потому что тренировочный prior ближе к test.


`oracle_predictions` ставит все positives выше всех negatives, что соответствует идеальнму ранжированию, это верхняя оценка.

| Сплит | NDCG@10 | Recall@10 |
|---|---:|---:|
| val | 1.0000 | 0.1085 |
| test | 1.0000 | 0.1020 |

NDCG@10 = 1.0 подтверждает, что функция `evaluate_ranking` считает метрику правильно. Recall@10 ограничен сверху: у пользователя в test много positives, а в топ-10 помещается только 10.

### Сравнение трёх моделей (test)

| Метрика | Dummy | CatBoost | Oracle |
|---|---:|---:|---:|
| LogLoss | 0.5966 | **0.2495** | — |
| ROC-AUC | 0.5000 | **0.9578** | — |
| NDCG@10 | 0.6811 | 0.9779 | 1.0000 |
| Recall@10 | 0.0780 | 0.1004 | 0.1020 |

По LogLoss CatBoost улучшает dummy на 58%. По ROC-AUC — с 0.5 до 0.958. 

По ranking-метрикам CatBoost почти достигает oracle: 0.978 из 1.000 по NDCG@10 и 0.1004 из 0.1020 по Recall@10. То есть 98% от идеала.

Причина — в текущей постановке 71.6% test-событий положительные. Модель, которая научилась отличать «сессионное» прослушивание от «одиночного», почти попадает в идеальное ранжирование.

Получается, что NDCG@10 и Recall@10 плохо различают модели, расстояние от baseline до oracle — всего 2%.

Чтобы решить эту проблему, попробуем обучить модель без признака, который "перевешивает все остальное" -- без u_days_since_last_event (т.е. сделаем ablation study).

## Ablation (3): вклад групп признаков

Скрипт `src/train_baseline_ablation.py` обучает одну и ту же CatBoost-модель на разных наборах признаков, чтобы понять, какие группы реально работают. Все 6 конфигураций обучаются на train, ранняя остановка по val, метрики считаются на test. Результаты test в таблице:

| Конфигурация | Признаков | LogLoss | ΔLogLoss | ROC-AUC | ΔROC-AUC | NDCG@10 |
|---|---:|---:|---:|---:|---:|---:|
| **full** (baseline) | 43 | **0.2495** | — | **0.9578** | — | **0.9779** |
| no_u_days_since_last_event | 42 | 0.4256 | +0.176 | 0.8446 | −0.113 | 0.8477 |
| no_recency | 38 | 0.4301 | +0.181 | 0.8412 | −0.117 | 0.8548 |
| no_user_features | 27 | 0.5216 | +0.272 | 0.7352 | −0.223 | 0.7921 |
| no_pair_features | 33 | 0.2567 | +0.007 | 0.9560 | −0.002 | 0.9681 |
| only_ctx | 3 | 0.5910 | +0.342 | 0.5714 | −0.386 | 0.6414 |

`full` воспроизводит baseline один-в-один — sanity-check пройден, ablation и baseline обучаются в идентичных условиях.

### Результаты

Удаление `u_days_since_last_event` обваливает качество сильнее, чем удаление любой другой группы: LogLoss растёт на 70% (с 0.2495 до 0.4256), ROC-AUC падает на 0.113 (с 0.9578 до 0.8446). Остальные признаки, относящиеся к отсчету "сколько времени прошло с последнего действия" (сессионный индикатор) бесполезны, поскольку LogLoss практически не меняется при удалении как одного из таких признаков, так и всех разом. То же самое относится и к парным признакам -- это, скорее всего, из-за разреженности этого признака. Только контекстные признаки дают точность на уровне Dummy, что тоже не делает их важными для наших предсказаний.

### Выводы

- Без сессионного индикатора модель находится на NDCG@10 = 0.848, ROC-AUC = 0.845 — заметно ниже полного baseline.
- С сессионным индикатором модель почти идеальна на ranking.

То есть baseline силён не за счёт «понимания персональной релевантности», а за счёт одного сильного сессионного сигнала, недоступного в ситуации реальной работы рекомендательной системы. Это честная характеристика, и её важно учитывать при сравнении с автоматической генерацией признаков.

**Две точки отсчёта для дальнейших сравнений:**

- Полный ручной baseline (LogLoss 0.2495) — «с сессионным индикатором».
- Честный ручной baseline (LogLoss 0.4256) — «без сессионного индикатора».

Автоматическая генерация признаков должна сравниваться с обеими. Если подход даёт LogLoss между 0.25 и 0.43 — это выигрыш над честным baseline, но не над полным. Если ниже 0.25 — выигрыш над полным. 

## Автоматическая генерация и отбор признаков

Скрипт `src/auto_features.py`. Вопрос: можно ли автоматизировать построение признаков и сохранить качество по сравнению с ручным baseline.

### Подход: DSL и grid search

Определяется ограниченный язык описания агрегатов (Domain Specific Language / DSL):

- **`group_by`** -- `{(uid,), (item_id,), (uid, item_id)}`;
- **`window_days`** -- `1, 3, 7, 14, 30`;
- **`metric`** -- `{listen_count, played_ratio_mean, like_count}`;
- **`recency`** —- время с последнего события (all / listen / like).

Все комбинации перебираются исчерпывающе, материализуются теми же примитивами `_window_sum` / `_recency_days`, что и ручные признаки — утечки невозможны по построению. Обучение CatBoost с теми же гиперпараметрами, что baseline, на том же временном сплите.

В качестве минимального приближения выбрала DSL: логика похожа и более удобно для тестового/учебного задания. Window days выбраны исходя из цикличных событий в календаре (неделя, две, месяц и более маленькие разбиения).

### Результаты

| Подход | LogLoss (test) | ROC-AUC (test) | NDCG@10 (test) |
|---|---:|---:|---:|
| `baseline_full` (ручной + сессионный индикатор) | **0.2495** | **0.9578** | **0.9779** |
| `baseline_honest` (ручной, без сессионного индикатора) | 0.4256 | 0.8446 | 0.8477 |
| `auto_all` (54 DSL-спец.) | 0.2667 | 0.9485 | 0.9538 |
| `auto_selected` (top-15 по важности) | 0.2665 | 0.9482 | 0.9473 |


### Выводы

**1. Grid search также сделал наиболее приоритетным признаком сессионный индикатор.** Важность -- `auto_uid_days_since_all` (23.6%) и `auto_uid_days_since_listen` (22.3%), аналоги ручного `u_days_since_last_event`, что подтверждает особенность исходных данных и что код собран корректно. 

**2. Отбор по важности почти не улучшил качество, но его можно использовать для сжатия модели.** `auto_selected` (top-15) даёт LogLoss 0.2665 против 0.2667 у `auto_all` — разница в пределах шума.

**3. Auto уступает полному ручному baseline**, поскольку DSL собрал более узкое число признаков, чем ручной перебор: нет `ctx_track_length_sec` / `ctx_log_track_length` / `ctx_is_organic` (11.6% важности в ручном baseline), нет all-time агрегатов, нет парных `mean_played_ratio`. Но следующим возможным шагом исследования может быть расширение DSL.

### Автоматический выбор временного окна

Для каждой пары `(group_by, metric)` обучены однофичевые модели по каждому окну из `{1, 3, 7, 14, 30}` дней. Оптимальное окно — то, что даёт минимальный LogLoss на validation.

Результат: **единого оптимального окна нет**, оно зависит от типа метрики и группы.

| Спецификация | LogLoss по окнам (val) | Лучшее |
|---|---|---:|
| `uid_played_ratio_mean` | 1d=0.4504, 3d=0.4657, 7d=0.4737, 14d=0.4846, 30d=0.4929 | 1d |
| `item_id_played_ratio_mean` | 1d=0.6112, 3d=0.6103, 7d=0.6089, 14d=0.6073, 30d=0.6044 | 30d |
| `uid_item_id_played_ratio_mean` | 1d=0.6100, 3d=0.6084, 7d=0.6054, 14d=0.6023, 30d=0.5981 | 30d |
| `uid_listen_count` | 1d=0.6046 … 30d=0.6136 | 1d |

Окно имеет значение прежде всего для `played_ratio_mean`. Для пользовательской метрики оптимально короткое окно (1 день) — вкусы меняются быстро, и свежее поведение пользователя сильнее всего предсказывает текущее. Для item и пары user–item оптимально длинное окно (30 дней) — популярность трека накапливается со временем.

**7 дней не является оптимумом ни для одной метрики.** Ручной выбор 7 дней был удобным приближением, но не оптимальным. Это численный ответ на вопрос задания. **Для каждой метрики получается свое лучшее окно**.

Это подтверждается и feature importance: `auto_uid_played_ratio_mean_1d` имеет важность 15.2%, а `_7d` — только 3.7%. CatBoost сам предпочёл окно 1d — согласуется с window sensitivity.

Для `listen_count` и `like_count` разница между окнами незначительна (~0.001–0.002 LogLoss): эти метрики не чувствительны к окну. Ценность автоматического подбора окна сосредоточена в `played_ratio_mean`.

### Направления развития

1. Все-таки стоит попробовать использовать ИИ-агента для автоматизации;
2. Выбор метрики, по которой в итоге стоит ориентироваться в рекомендательной системе, можно доверить либо сотруднику, либо также ИИ-агенту;
3. Попробовать использовать SHAP и другие методы ранжирования признаков для более глубокого анализа работы модели на имеющихся данных, но в таком случае стоит использовать датасет побольше;
4. Вместо детерминированных WINDOWS_DAYS можно написать генератор для значений окон (с ограничениями на рандомайзер).

### Вывод

Автоматическая генерация через grid search по DSL:

1. Воспроизводит ключевой сигнал ручного baseline (сессионный индикатор).
2. Автоматически подбирает оптимальное окно для каждой метрики.
